# netCatalog

CLI на Go для получения доменов, IP-адресов и CIDR-подсетей сервисов.
Подключены публичный [iplist](https://github.com/rekryt/iplist) и готовая YAML-выгрузка
[v2fly/domain-list-community](https://github.com/v2fly/domain-list-community).
Кеша нет: каждая команда получает данные по HTTP. Программа **не меняет маршруты роутера**.

## Сборка

Нужен Go 1.22 или новее. На macOS его можно установить самостоятельно через
`brew install go` либо скачать с <https://go.dev/dl/>.

```sh
go build -o bin/netCatalog ./cmd/netCatalog
go test -race ./...
go vet ./...
```

Вместо сборки можно запускать `go run ./cmd/netCatalog ...`.
Для команд и help используется Cobra, для определения терминала —
`golang.org/x/term`, для разбора YAML — `gopkg.in/yaml.v3`.
Тесты используют стандартный `testing` и Testify (`assert`/`require`).
Версии зависимостей совместимы с Go 1.22 и зафиксированы в `go.mod` и `go.sum`.

## Форматирование и линтер

Нужны `make`, `gofmt` (входит в установку Go) и **golangci-lint v2.14.0**.
Версия линтера закреплена в `Makefile`: другая версия будет отклонена,
чтобы набор проверок не зависел от окружения разработчика.
Используем готовый бинарный релиз линтера, поэтому Go 1.22 проекта не нужно
обновлять ради сборки самого инструмента. Линтер не добавляется в `go.mod`.

Установка закреплённой версии на macOS/Linux в локальный, исключённый из Git `bin/`:

```sh
curl -sSfL https://raw.githubusercontent.com/golangci/golangci-lint/v2.14.0/install.sh \
  | sh -s -- -b ./bin v2.14.0
export PATH="$PWD/bin:$PATH"
```

Либо скачайте готовый архив для своей платформы из
[релиза v2.14.0](https://github.com/golangci/golangci-lint/releases/tag/v2.14.0)
и проверьте SHA256 по опубликованному файлу checksums.

```sh
make fmt        # применить gofmt к cmd/ и internal/
make fmt-check  # проверить форматирование без изменения файлов
make lint       # запустить golangci-lint для кода и тестов
make check      # fmt-check, затем lint; не изменяет исходники
go test -race ./...
```

Если инструменты не находятся в `PATH`, можно указать их явно:

```sh
make check GOFMT=/path/to/gofmt GOLANGCI_LINT=/path/to/golangci-lint
```

Сам `go` должен оставаться в `PATH`: линтер использует его для загрузки пакетов.

В `.golangci.yml` включены `govet`, `staticcheck`, `errcheck`, `revive` и
`testifylint`: ошибки кода, непроверенные ошибки, стиль/GoDoc и использование
Testify. Тестовые файлы не исключаются. `make check` не запускает тесты:
их проверяем отдельной командой выше. Папка `docs/` остаётся историей;
форматирование её не затрагивает.

## Использование

```sh
# Динамический каталог порталов iplist и имён списков v2fly
bin/netCatalog services list
bin/netCatalog services search telegram
# telegram и telegram.org (если они присутствуют в выбранных источниках)

# Домены: по одному на строку, без префиксов
bin/netCatalog get youtube --type domains

# Показать предупреждения (оранжевые в терминале, в stderr)
bin/netCatalog get telegram --type domains --info

# Объединить список discord из v2fly и порталы discord.* из iplist
bin/netCatalog get discord --type domains

# Отдельные IP / подсети; IPv4 по умолчанию
bin/netCatalog get youtube --type ips
bin/netCatalog get youtube --type cidrs --family ipv4
bin/netCatalog get youtube --type cidrs --family ipv6
bin/netCatalog get youtube --type ips --family all

# Точный домен имеет приоритет перед поиском по подстроке
bin/netCatalog get youtube.com --type domains

# Низкоуровневый запрос без загрузки каталога
bin/netCatalog get youtube.com --site --type domains

# Собственный экземпляр iplist или другой публичный портал
bin/netCatalog get youtube --type ips --url https://iplist.opencck.org/ --timeout 15s

bin/netCatalog sources list
bin/netCatalog --help
```

Каталог строится из источников при каждом вызове, без заданных вручную соответствий.
Запись — портал с доменом (`telegram.org`) либо именованный список (`telegram`).
Домен для имени списка не угадывается и не задаётся вручную.
Группы iplist (`messengers`, `youtube` и т. п.) не участвуют в поиске и выборе сервиса.
`services search telegram` ищет подстроку в доменах и именах списков и выводит
идентификаторы по одному на строку; соседние порталы группы iplist не добавляются.

`get` сначала ищет точное совпадение домена. Короткое имя без точек (`discord`)
выбирает **все** порталы, чья первая часть имени целиком совпадает: `discord.com`,
`discord.gg`, `discord.media`. `discord-tools.com`, `notdiscord.com` и
`cdn.discord.com` не подходят. Для каждого портала запрашиваются данные, затем
списки объединяются с удалением дубликатов. При запросе доменов добавляется также
именованный список `discord` из v2fly. Для `ips` и `cidrs` используется только iplist;
v2fly при таких командах не загружается. Сбой одного источника или портала не мешает
вернуть данные остальных. Сервис, который есть только в v2fly, также доступен по имени.

Если совпадений по первой части нет, используется прежний поиск по подстроке:
единственное совпадение выбирается, несколько дают код `2` с предложением уточнить
домен. Неизвестное имя также даёт код `2`. `get discord.com` получает данные только
этого портала iplist, без подключения всего списка `discord` из v2fly.
`services search` выводит отдельные найденные идентификаторы.

Совпадение первой части — **эвристика**, а не подтверждение общего владельца доменов.
Соответствия не задаются вручную; разные имена одной компании автоматически не объединяем.

Каталог iplist ограничен выбранным HTTP-порталом; другие порталы могут содержать
другие доменные идентификаторы. Его API не предоставляет отдельного лёгкого каталога:
`services list/search` и обычный `get` получают полную JSON-выгрузку, используя
метаданные. Затем `get` запрашивает выбранные порталы через `site=`.
Флаг `--site` позволяет пропустить обнаружение и передать домен прямо в iplist;
v2fly при этом не вызывается.

Внутренний каталог хранит имена, необязательные домены и привязки к источникам. Привязки содержат
идентификатор источника и его непрозрачный
ключ: для iplist это портал, для v2fly — имя списка, для будущего источника это может быть файл или ID.
Одинаковые домены разных источников объединяются с сохранением всех привязок;
их внутренние ключи не участвуют в пользовательском поиске.

В примерах флаги указываются после команды и позиционного аргумента.
Cobra формирует help для каждой команды: `netCatalog get --help`,
`netCatalog services search --help`. Help не обращается к HTTP-источникам.
`--type` обязателен. `--family` имеет значения `ipv4`, `ipv6`, `all` и запрещён для доменов.
Флага `--format` нет: вывод всегда текстовый, одна запись на строку.

### Вывод и ошибки

- Данные — в `stdout`, предупреждения — в `stderr`.
- По умолчанию предупреждения скрыты: `get` выводит только домены, IP или CIDR.
  Флаг `--info` включает предупреждения для `get` и `services list/search`.
  В терминале они оранжевые (ANSI 256-color, цвет 208); при перенаправлении `stderr`
  в файл/pipe, наличии переменной `NO_COLOR` (в том числе пустой) или `TERM=dumb`
  используются обычные строки без ANSI-кодов. Для определения терминала используется
  `golang.org/x/term`, без собственных платформенных системных вызовов.
- Неудачные запросы и некорректные записи пропускаются. Например, при сбое IPv6
  команда с `--family all` всё равно вернёт полученные IPv4.
- Код завершения `0`: хотя бы один успешный запрос, в том числе пустой или частичный результат.
- Код `1`: недоступен весь каталог/все запросы данных неудачны либо невозможно записать результат.
- Код `2`: неверные аргументы, неизвестный или неоднозначный сервис.
- Ошибки аргументов и полный сбой получения каталога/данных всегда видны в `stderr`,
  даже без `--info`. При частичном результате код остаётся `0`, а подробности
  пропущенных запросов видны только с `--info`.
- Таймаут по умолчанию — 30 секунд **на запрос**. IPv4 и IPv6 запрашиваются
  последовательно и независимо. Ctrl+C отменяет текущий запрос.
- Ответ iplist ограничен 64 MiB, YAML-релиз v2fly — 32 MiB.
  Повреждённый формат/схема считается неудачным запросом соответствующего источника.
- Результат сортируется, точные дубликаты удаляются.

Домены, IP и CIDR выводятся по одному на строку без префиксов и метаданных.
Например, список доменов:

```text
discord.com
discord.gg
```

Это список значений, **не готовый файл импорта в Keenetic**. Тип доменного правила
сохраняется во внутренней модели, но не выводится в CLI. Адаптер по-прежнему
использует JSON для обмена с iplist; пользовательский JSON-вывод удалён.

## Источник v2fly

По умолчанию используется готовая выгрузка последнего релиза:

```text
https://github.com/v2fly/domain-list-community/releases/latest/download/dlc.dat_plain.yml
```

- Исходники `data/` не читаются: включения и affiliations уже обработаны upstream.
- Имена, начинающиеся с `category`, и любые имена с дефисом исключены из каталога.
  Это временный фильтр: дефис не обязательно означает сборку нескольких сервисов.
- Возвращаются **только `domain`-правила**. `full`, `keyword`, `regexp` игнорируются;
  сведения о пропусках видны с `--info`.
- Атрибуты в строках вида `domain:example.com:@ads` не попадают в доменное имя.
- Имена списков используются как имена сервисов; соответствий `discord → discord.com`
  в коде нет. Списки, доступные только в v2fly, не зависят от каталога iplist.
- Вся выгрузка загружается один раз на команду и остаётся только в памяти до её завершения.
  Между вызовами данные не сохраняются и не переиспользуются.
- Другую выгрузку можно указать через `--v2fly-url URL`, например закреплённый релиз.
  `--v2fly-url ''` отключает этот источник для конкретной команды.

```sh
bin/netCatalog get discord --type domains
bin/netCatalog get discord --type domains --info
bin/netCatalog get discord --type domains --v2fly-url ''  # только iplist
```

## Важно для Keenetic

JSON-контроллер upstream iplist экспортирует **исходные** `cidr4/cidr6`, не применяя
его `replace`-замены широких сетей более узкими. CLI сохраняет этот смысл и
показывает предупреждение при запросе CIDR с `--info`. Большая подсеть может включать другие сервисы:
не следует без проверки направлять всю выгрузку через VPN. Отдельные IP также
могут принадлежать общей CDN-инфраструктуре; полнота и свежесть зависят от upstream.

CLI не делает DNS/WHOIS-запросов и не расширяет сети. CIDR приводятся к сетевому
адресу (`192.0.2.123/24` → `192.0.2.0/24`), но не объединяются в более широкие сети.
Публичному HTTP-источнику передаётся имя выбранного портала, а не группы.

Генерация команд Keenetic — следующий отдельный этап: нужно выбрать способ импорта,
целевой интерфейс/шлюз и правила обновления ранее добавленных маршрутов.

## Структура и аналогии с Kotlin

```text
cmd/netCatalog/main.go         точка входа, Ctrl+C, код завершения
internal/cli/                 команды Cobra, коды завершения и вывод
internal/resolver/            модели, Provider, динамический каталог и объединение
internal/providers/iplist/    HTTP-адаптер и проверка записей
internal/providers/v2fly/     YAML-релиз, фильтры списков и domain-правил
```

- `struct` хранит поля, как простой Kotlin-класс, но не генерирует `copy/equals` как `data class`.
- `Provider` — интерфейс. Go-тип реализует его **неявно**, если имеет нужные методы;
  объявления `: Provider` нет.
- `Service` — внутренняя модель, а не DTO iplist. `Binding.Key` интерпретирует только
  соответствующий адаптер, подобно преобразованию внешнего DTO в доменную модель Kotlin.
- `New(...)` — обычная функция-конструктор, через неё передаём HTTP-клиент.
  Контейнер зависимостей не нужен.
- `(Result, error)` — явный возврат результата и ошибки вместо исключений.
- `context.Context` передаёт отмену выполнения; это не аналог всей системы корутин.
- `net/netip` предоставляет типы IP и CIDR, чтобы не проверять адреса вручную строками.
- `internal` запрещает импорт этих пакетов из других Go-модулей.
- `httptest.NewServer` позволяет проверять интеграцию локально, без публичного портала.

### Добавление источника

1. Создать пакет `internal/providers/<source>` с реализацией `resolver.Provider`.
2. Реализовать `ListServices`: обнаруживать доменные идентификаторы или именованные
   списки (`Service.Name`, если домена нет) и их привязки `Binding{Source, Key}`.
   Если источник не сообщает домен, не угадывать его по имени.
3. Реализовать `Fetch(ctx, key, query)`: интерпретировать свой ключ и переводить данные
   в `Entry`, сохраняя тип доменного правила. Зарегистрировать адаптер в
   `Resolver.Providers` в CLI; при необходимости добавить параметры его подключения.
4. Добавить тесты. Resolver уже объединяет результаты нескольких адаптеров,
   сохраняет источники и не смешивает `full` и `suffix` для одного домена.

Новый URL существующего iplist-формата задаётся через `--url`; новый формат требует
нового адаптера. Динамических плагинов и хранения данных нет.

## Тесты и документация кода

- Одна функция `Test<Method><Scenario>` проверяет один метод и один сценарий.
  Для разных условий создаются отдельные функции, без таблиц сценариев и вложенных `t.Run`.
- Несколько assertions допустимы для одного сценария. `require` проверяет условия,
  без которых тест не может продолжаться; `assert` — независимые ожидания.
- Общая подготовка находится в тестовых helpers с `t.Helper()` и `t.Cleanup()`.
  HTTP проверяется локальными серверами `httptest`, без публичных источников.
- Экспортируемые символы и пакеты документируются в формате GoDoc:
  комментарий перед объявлением, начиная с имени символа или `Package <name>`.
  Комментарии описывают контракт, ошибки, ограничения и частичные результаты.
  Документацию можно читать через `go doc ./internal/resolver` и подсказки IDE.
